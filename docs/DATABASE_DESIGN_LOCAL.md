# 本地演示数据库设计

## 设计边界

当前业务代码明确依赖 MySQL 8.0 的 `information_schema`、`EXPLAIN FORMAT=JSON`、
`DATE_FORMAT`、`YEAR` 和 `QUARTER`，因此本地业务库采用 MySQL，而不是 SQLite。
平台自身的用户、会话、收藏、问数快照和审计仍由应用写入 SQLite。

代码白名单包含 `regions`、`categories`、`products`、`customers`、`orders` 和
`order_items` 六张业务表。虽然原任务建议设计 3～5 张表，但删除任意一张都会破坏
规则模式内置查询；本设计以“不改业务逻辑”为更高优先级，保留全部六张表。

## 业务模型

```text
regions 1──N customers 1──N orders 1──N order_items N──1 products N──1 categories
```

- `regions`：销售区域。区域归属跟随客户，而非订单收货地址。
- `categories`：商品细分类目。
- `products`：商品主数据，保留标准售价、标准成本和在售标记。
- `customers`：演示客户，包含区域、客户分层和注册日期。
- `orders`：订单事实，保存状态、时间、渠道和明细折后金额合计。
- `order_items`：订单行，保存交易发生时的单价与折扣，避免商品调价影响历史数据。

## 本地样例数据规模

阶段 3 的初始化器按固定随机种子 `20261104` 生成：

| 表 | 目标行数 | 设计说明 |
| --- | ---: | --- |
| `regions` | 50 | 省级销售区域，满足每表至少 50 行的目标 |
| `categories` | 50 | 办公、数码、家居、食品、运动等细分类目 |
| `products` | 150 | 每个细分类目 3 个商品，价格与毛利率分布不同 |
| `customers` | 250 | 覆盖四种客户分层和不同注册月份 |
| `orders` | 360 | 覆盖 2025-01 至 2026-10，含季节、周末和渠道差异 |
| `order_items` | 500 | 每单至少一行，部分订单包含多件不同商品 |

订单状态覆盖 `PAID`、`REFUNDED`、`CANCELLED` 和 `PENDING`；支付时间不早于下单
时间；订单金额逐分等于明细折后金额合计。数据包含复购、跨区域、不同渠道、季度变化、
退款和近期未支付订单，支持聚合、多表连接和时间过滤。

## DDL 与索引

完整建表语句位于 `database/schema.sql`。除主键和外键外，设计包含：

- 业务名称与订单号唯一约束；
- 订单时间/状态双向组合索引；
- 客户区域、分层和注册日期索引；
- 商品品类、订单客户、订单渠道和明细商品索引；
- 金额、数量、折扣、状态、支付时间和在售标记检查约束；
- 所有业务字段与数据表的中文注释，供元数据目录直接读取。

## 查询验收集

`database/expected_queries.sql` 保存十条只读验收 SQL，与规则模式的十个示例问题一一
对应。验收范围覆盖月度趋势、区域对比、商品排行、品类汇总、渠道分布、客户分层、
新增客户、毛利、订单计数和退款率。

这些查询全部显式选择字段，不访问系统库，不使用写语句，并且仅引用六张白名单业务表，
可通过项目的 SQL Guard。三表连接会进入 L1 人工确认，四表连接会进入 L2 管理员审批，
这是现有安全策略的预期行为。

## 数据口径

- 销售额：`orders.status = 'PAID'` 的订单金额，或相应订单明细折后金额。
- 客单价：已支付订单 `amount` 的平均值。
- 毛利：明细折后收入减去商品标准成本，不含物流、营销、税费等间接成本。
- 退款率：当年 `REFUNDED` 订单数除以当年全部状态订单数。
- 新增客户：按 `customers.registered_at` 统计。
- “今年”和“本季度”：使用 MySQL `CURRENT_DATE`，初始化数据覆盖当前验收年份 2026。
